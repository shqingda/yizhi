## 1. 简历上的项目经历

**一纸简历｜独立开发的在线简历编辑器**

技术栈：React、TypeScript、Vite、Tailwind CSS、Base UI、Cloudflare Workers。

- 独立实现表单编辑、栏目排序与隐藏、照片处理、多份草稿管理及实时预览；支持手机编辑 / 预览切换和浅色、深色主题。
- 基于真实 DOM 测量进行 A4 分页，尽量保持栏目标题和首条内容同页；提供保留文字的浏览器打印，以及整页截图生成的长页 PDF。
- 实现本机自动保存、旧草稿迁移、撤销重做、删除恢复与替换前备份；存储失败时保留当前内容并提供 JSON 备份入口。
- 按栏目拆分表单，统一编辑与预览的草稿状态，按需加载示例与 PDF 依赖，并通过测试和构建体积预算控制回归。

量化结果引用 [重构验收](qa/2026-10-02-refactor.md) 的实测数据。不要把构建脚本变小直接说成页面加载速度提高了同样比例；首次用户还需要下载示例 JSON。

## 2. 一分钟介绍

“我做了一个在线简历编辑器，主要解决填写、调整排版和导出之间来回修改的问题。用户左侧编辑，右侧即时预览，能管理多份草稿，导出 A4 PDF 或长页 PDF。

当前版本不需要登录，数据只存在浏览器。保存方面做了防抖自动保存、错误提示、撤销重做和导入前恢复点，重点是避免用户误操作后找不回内容。

技术上我主要处理了两件事：一是把真实内容高度转换成 A4 分页，同时处理照片和字体加载后的重新测量；二是让编辑页、预览页和导出使用同一份数据，避免预览不是最新版本。后续又拆分了大型表单，移除了不再使用的云端代码，并把示例照片从首屏脚本里移出去。”

## 3. 技术分别负责什么

| 技术 | 在本项目中的作用 |
| --- | --- |
| React | 管理草稿状态、表单与预览组件，通过不可变更新触发界面变化。 |
| TypeScript | 约束 Resume、栏目、草稿和恢复点的数据结构。 |
| Vite | 开发服务、生产构建、按动态导入拆分资源。 |
| Tailwind CSS | 编辑器布局与主题；简历排版另有专用 CSS。 |
| Base UI | 菜单、弹窗、按钮等基础交互与焦点行为。 |
| localStorage | 同一浏览器、同一站点下的草稿与偏好持久化。 |
| modern-screenshot / jsPDF | 需要图片 PDF 时按需加载，截图后写入 PDF。 |
| Cloudflare Workers | 托管静态资源、SPA 路由回退，以及健康检查和旧 API 停用响应。 |
| Vitest | 数据规范化、保存与恢复、加载失败、分页和导出的自动化验证。 |

当前 Worker 不处理用户简历，也不需要数据库。旧版 Hono、Drizzle 和 D1 已移除运行依赖。

## 4. 为什么统一数据源

`WorkspaceProvider` 放在路由外，内部只有一个 `useResume`。编辑页负责改变数据，预览页读取同一个状态，`ResumeDocument` 把数据渲染出来。这样返回编辑后仍可撤销，也不需要预览页自己重新拼装草稿。

“单一数据源”不是所有内容都塞进一个组件。数据生命周期集中在工作区，UI 则按页面、面板和栏目拆分。JSON 文件处理、存储、分页、导出各自有清楚的职责。

## 5. 自动保存和数据保护

**为什么防抖 350ms？** 用户输入时先更新内存和预览，短暂停顿后再序列化写入浏览器，减少同步存储操作。页面隐藏、离开应用和主动预览时再尽力刷新。

**保存失败怎么办？** 捕获存储不可用或容量不足，显示失败，不把失败标为成功；内存内容仍可导出 JSON。浏览器崩溃时不能保证尚未写入的数据安全。

**为什么工作区一次写入？** 当前草稿 ID、草稿内容和恢复点放在同一个 JSON 记录中，一次 `setItem` 更新，避免分多次写入后出现指针和内容不对应。

**旧数据怎么处理？** 优先读新版工作区，没有新版时读旧键，规范化后保留原值作为迁移来源。读取损坏数据时停止写入，不用示例覆盖。

**撤销和恢复点有什么区别？** 撤销是当前会话中的内存历史，适合日常输入；恢复点是重要替换前的持久副本，可跨刷新。恢复点受数量与容量限制，不是无限版本历史。

**多标签页会怎样？** 当前没有冲突合并，不应宣称支持并发安全编辑。可作为下一步增加版本比较和冲突提示的方向。

## 6. 为什么分页需要测量

同样字数会因字体、字号、宽度、图片和换行产生不同高度。先把简历渲染成 DOM，测量内容块及间距，再用纯函数按 A4 的可用高度计算分页。

标题与首条内容尽量一起判断，普通经历尽量整块换页；超过一页的经历需要允许自然跨页。图片和字体加载后重新测量，避免按占位尺寸分页。

将“浏览器测量”和“数字计算”分开，方便用单元测试覆盖边界：空内容、恰好一页、标题落页尾、多页以及单条内容超高。最终打印仍必须实测，因为不同浏览器的字体和打印规则会变化。

## 7. 两种 PDF 的取舍

A4 路径把简历复制到隔离 iframe，等待样式、字体和照片，再调用浏览器打印。它通常保留文字，适合投递，但最终纸张、缩放和页眉页脚由用户的打印选项决定。

长页路径把简历截成图片再装入 PDF，保留连续视觉效果，但文字不能复制，过长文档还受到图片和 PDF 尺寸限制。这两条路径没有服务端渲染。

用户预览缩放只作用于界面容器，导出使用实际纸张宽度，因此不能直接把缩放后的屏幕截图当成 A4 成品。

## 8. 包体积和渲染优化怎么解释

先记录原始构建产物，再找来源。这个项目的大示例包含内嵌照片，原来与应用一起进入 JavaScript。现在保留原始 JSON 文件作为单一模板来源，只有首次使用或重置时请求；已有草稿无需再下载示例。

编辑页面按路由拆分，图片 PDF 库按导出动作加载。浏览器已加载的编辑页切换预览无需额外页面脚本。构建预算累计入口、编辑页面及所有静态依赖，防止只移动文件却声称总体变小。

`ResumeDocument` 跳过草稿未改变时的无关渲染，分页测量直接依赖不可变的数据对象，避免重复序列化大照片。这些优化减少脚本解析和重复计算；没有实际性能测量时，不声称改善了具体毫秒数或首屏指标。

## 9. 怎么验证，哪些还没验证

`pnpm check` 包含类型检查、Vitest、生产构建和包体积预算。测试聚焦失败时的行为：示例网络失败重试、损坏存储不覆盖、配额失败、草稿隔离、替换前恢复点、异步重置期间的新编辑保护。

浏览器操作检查用户完整流程，而不是只看组件是否渲染。真实手机软键盘、屏幕阅读器和复杂系统打印仍需要独立验收，准确范围见 [待办](ux-plan.md)。

## 10. 面试练习顺序

先用一分钟讲清用户流程，再各用一个例子说明保存失败保护和分页处理。最后准备回答边界：为什么没有云同步、多标签页如何冲突、为什么图片 PDF 不可复制、为什么单元测试不能替代打印验收。

代码阅读顺序见 [架构文档](architecture.md)。讲重构时强调职责与行为变化，避免把删除依赖、拆文件数量当成最终用户价值。
