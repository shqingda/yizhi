## 一、放在简历上的项目经历

**一纸简历｜独立开发（个人项目）**

技术栈：React、TypeScript、Vite、Tailwind CSS、Hono、Drizzle ORM、Cloudflare Workers、D1

- 独立开发在线简历编辑器，支持填写经历、拖动栏目和联系方式调整顺序、隐藏内容、照片及版式设置、JSON 导入导出；编辑时即时预览，并提供公开分享页。
- 根据页面中内容的实际高度进行 A4 分页，将栏目标题和第一条内容一起判断，减少标题单独留在页尾的情况；支持保留文字的 A4 打印，以及将整份简历转成图片后生成的长图 PDF。
- 使用 Hono 编写读写接口，通过 Drizzle 和 D1 保存简历；加入浏览器本地自动保存和云端版本检查，检测到旧版本保存冲突时，保留本地草稿并提示用户处理。

下面的详解逐项对应这三条。“实时预览”“分页”“版本检查”等词，都会解释它到底做了什么。

## 二、面试一上来：“介绍一下你的项目”

### 2.1 一到两分钟的开场，可以照着练

> 我独立做了一个在线简历工具，叫一纸简历，已经部署到 Cloudflare 上了。这是个人项目，编辑界面、简历排版、导出、后端接口和数据库都是我负责的。
>
> 它的使用方式比较直接：用户填写基本信息、工作经历和项目经历，旁边就能看到排好的简历。还可以拖动栏目改变顺序，隐藏暂时不想展示的内容，调整照片和基本信息的位置。完成后可以导出 PDF，也可以通过链接分享。
>
> 技术上，前端用 React 和 TypeScript，React 负责表单和预览，TypeScript 用来约束数据结构。Vite 负责开发和打包，Tailwind 负责编辑界面的样式。后端用 Hono 提供保存和读取接口，通过 Drizzle 操作 Cloudflare 的 D1 数据库，接口运行在 Workers 上。
>
> 实现上，我把整份简历保存在一份数据里。用户修改表单后，预览直接根据新数据更新；编辑页和分享页共用同一个简历组件，避免两套排版分别维护。
>
> 我重点处理了两个问题。一个是 A4 分页：不同内容占的高度不一样，所以先测量实际高度，再决定哪里换页，并且让栏目标题尽量和第一条内容放在一起。另一个是保存：除了云端保存，也保留浏览器本地草稿；如果发现另一个页面已经更新过云端，就先保留当前修改，提示用户决定是否覆盖。

讲到这里先停，让面试官选他感兴趣的部分。不要一口气把后面所有细节都说出来。

这段介绍的顺序是：**项目是什么 → 你负责什么 → 用户怎么用 → 技术各做什么 → 怎么实现 → 两个重点问题。**

### 2.2 如果只给你三十秒

> 这是我独立开发的在线简历工具，用 React 和 TypeScript 做编辑和实时预览，用 Hono、Drizzle 和 Cloudflare D1 做云端保存。用户可以调整内容、顺序和版式，然后导出 PDF 或通过链接分享。我重点做了按实际内容高度进行 A4 分页，以及本地草稿和云端保存冲突的处理。

### 2.3 如果接着问：“为什么做这个项目？”

可以先讲它要解决的具体问题：

> 简历内容会反复修改，改完还要重新调顺序、检查分页。我希望把填写内容和排版分开：用户专心写经历，工具负责展示、保存和导出。

这是对产品用途的概括。你真正开始做它的原因，例如自己求职时遇到了什么问题，要补充真实经历，不必编一个故事。

### 2.4 如果接着问：“你个人做了哪些？”

> 我负责从前端到后端的完整实现。前端包括表单编辑、拖动排序、简历预览和 PDF 导出；后端包括读取和保存简历的接口、数据表和版本检查；最后把前端页面和后端接口部署到 Cloudflare。

“独立开发”不等于所有基础工具都自己造。React、图标库、PDF 库是现成工具；你做的是把它们组合起来，并实现这个项目自己的数据、排版和保存逻辑。

## 三、“用了什么技术？这些技术分别干什么？”

### 3.1 先把前端和后端分清楚

**前端**是用户在浏览器里能看到和操作的部分，例如输入框、拖动按钮和简历预览。

**后端**接收浏览器发来的请求，例如“保存这份简历”“把这份简历给我”。它再去读取或修改数据库。

**数据库**用来长期保存数据。关闭网页以后，云端简历仍然保存在那里。

一次完整操作可以这样理解：

```text
用户修改手机号
    ↓
React 更新当前简历数据 → 预览立刻显示新号码
    ↓
稍后保存到浏览器本地，同时安排云端保存
    ↓
浏览器把数据发给 Hono 接口
    ↓
接口检查数据和版本，通过 Drizzle 写入 D1
    ↓
别人打开分享链接 → 接口读取 D1 → 页面显示已保存的简历
```

注意：预览不需要等待云端保存成功。分享页读取的是已经保存的数据，不会自动跟随另一个人的键盘输入变化。

### 3.2 前端技术：先知道它在这里负责什么

| 名词 | 用人话解释 | 面试时怎么结合项目说 |
| --- | --- | --- |
| React | 把界面拆成组件，再根据数据生成界面的工具 | “表单和预览都读取当前简历数据，数据改变后，React 更新界面。” |
| 组件 | 一块可以重复使用的界面及其逻辑 | “我把简历正文做成一个组件，编辑页和分享页都使用它。” |
| TypeScript | 在 JavaScript 上增加类型检查，帮助开发时发现字段写错、类型不对等问题 | “我定义了简历和接口返回值的结构，减少不同模块传错数据。” |
| Vite | 开发时启动网站，发布时把源代码打包成可部署文件的工具 | “本地开发和生产构建都通过 Vite。” |
| Tailwind CSS | 通过现成的样式类设置间距、颜色、布局等 | “主要用于编辑器界面；简历纸张和打印样式另外写了专门的 CSS。” |
| React Router | 根据浏览器地址决定显示哪个页面 | “编辑器和公开简历是不同地址，对应不同页面。” |
| Lucide | 提供电话、邮箱、地点等图标的库 | “我按联系字段选择图标，再统一图标尺寸和文字对齐方式。” |
| shadcn 风格组件 / Base UI | 仓库里复用的按钮、菜单等界面组件，以及部分底层交互能力 | “基础控件用现有组件，简历编辑和排版逻辑自己实现。” |

**为什么没用 Zustand？** Zustand 是额外的状态管理库，也就是另一种集中保存和更新前端数据的工具。本项目主要用 React 自带的状态和自己封装的 `useResume` 管理简历，目前没有使用 Zustand。面试时不要把比亚迪项目的技术栈直接搬过来。

### 3.3 后端与部署技术：这四个名字不是一回事

| 名词 | 用人话解释 | 在这个项目里负责什么 |
| --- | --- | --- |
| Hono | 帮你编写后端接口的框架 | 分清“读取”和“保存”请求，取出参数，调用数据库，返回结果。 |
| Drizzle ORM | 帮你用 TypeScript 描述数据表、编写数据库操作的工具 | 查询简历、插入新简历、更新已有简历。ORM 可以理解为连接程序对象与数据库操作的一层工具。 |
| Cloudflare D1 | Cloudflare 提供的、基于 SQLite 的数据库服务 | 实际存放简历内容和更新时间。 |
| Cloudflare Workers | Cloudflare 提供的代码运行环境 | 运行 Hono 接口；本项目也通过配置一起发布前端文件。 |
| Wrangler | 与 Cloudflare 项目交互的命令行工具 | 把构建后的项目发布到 Cloudflare，并配置数据库绑定。 |

把关系记成一句话：**Hono 处理请求，Drizzle 操作数据库，D1 存数据，Workers 运行后端代码。**

### 3.4 “为什么这样选技术？”怎么回答

下面是结合项目规模能说明的取舍；只有符合你真实选择过程的部分，才说成当时的原因。

> 这个项目主要是表单编辑和文档展示，用 React 方便把界面拆分并复用。前后端都使用 TypeScript，可以共用简历的数据定义。后端的核心需求是整份简历的读取和保存，所以用 Hono 编写接口，通过 Drizzle 访问 D1。前端和接口都部署到 Cloudflare，不需要自己维护一台服务器的系统环境。

**Serverless 是什么？** 通常译为“无服务器”。意思是服务器的运行和维护交给平台，你主要提交代码和配置；实际仍然有服务器在运行，不是程序凭空执行。

不要说这套技术是“性能最强”或“高并发最优方案”。本项目没有做这样的对比测试，说明它适合当前需求即可。

## 四、第一条经历怎么讲：编辑、排序、版式和分享

### 4.1 “你怎么组织简历数据？”

**先用例子理解：** 一份简历既有内容，也有显示偏好。姓名和工作经历属于内容；“先展示项目还是教育”“隐藏邮箱”“照片放左边”属于显示偏好。

代码里把它们放在同一个对象的不同位置。对象可以理解为“按名称存放不同内容的一份记录”：

```ts
// 简化示意，只列出需要理解的字段，不是完整的简历文件。
const resume = {
  basics: { name: "张三", phone: "13800000000" },
  experience: [{ id: "work-1", company: "某公司", position: "前端开发" }],
  meta: {
    sectionOrder: ["experience", "education"],
    hiddenBasics: ["email"],
    headerAlign: "left",
  },
};
```

`basics` 是基本信息，`experience` 是工作经历列表，`meta` 是显示配置。数组就是有先后顺序的列表，比如这里先显示工作，再显示教育。

**面试可以这样答：**

> 我把简历内容和显示配置分开保存。隐藏或排序只修改显示配置，原来的经历和联系方式还在。这样用户切换版式时不用重新填写内容。

### 4.2 “实时预览怎么做？为什么输入就会变？”

**State，也就是状态**，是 React 当前记住的数据。本项目里最重要的状态就是当前这份简历。

输入框和预览读取同一份状态。改手机号时，先更新其中的 `phone`，React 再用新数据更新预览。这个过程就在浏览器里完成。

下面是更新基本信息的简化示意：

```tsx
setResume((current) => ({
  ...current,
  basics: { ...current.basics, phone: "13900000000" },
}));
```

逐句理解：`current` 是修改前的简历；`...current` 保留其他内容；`...current.basics` 保留姓名、邮箱等字段；最后只换掉手机号。外层和基本信息都生成新对象，交给 React 更新。

**受控表单**指输入框的值由 React 状态决定，输入时也通过更新状态来改变它。好处是输入框和预览有同一个数据来源，不用各维护一份再互相对照。

**Hook 是什么？** React 提供的一类函数，用来让组件记住数据、处理保存等行为。项目里的 `useResume` 是自己封装的 Hook，把简历数据、读取和保存逻辑集中放在一起，页面只调用它。

**面试可以这样答：**

> 实时预览没有额外调用服务器。我用 React 状态保存当前简历，表单更新状态，预览组件根据这份状态显示内容。网络保存是另一条流程，所以输入反馈不需要等接口。

### 4.3 “为什么要共用简历组件？”

编辑器预览和公开页都用 `ResumeDocument`，它负责把简历数据排成页面。

例如这次修改“工作经历只显示职位，不再追加地点”，只需改这一处渲染规则。编辑预览、分享页和以它为基础的导出都会使用同一套规则。

**面试可以这样答：**

> 如果编辑页和分享页分别写一套简历，就容易改了一边、漏了另一边。我把正文排版集中成一个组件，两边只负责提供数据。

“共用组件”不代表共用一个正在运行的页面；也不代表两个浏览器会实时同步输入。

### 4.4 “拖动排序怎么实现？”

**先想一个操作：** 用户把“项目经历”从第三位拖到第一位，变化的是栏目顺序，不是项目内容。

实际处理过程是：

1. 按下拖动手柄，记住正在拖哪一项。
2. 移动时，取得各行在屏幕上的位置。
3. 看指针最接近哪一行的中间，把那一行作为新位置。
4. 生成新的顺序数组，更新配置；预览按新顺序显示。
5. 松开或取消拖动后，结束处理并移除移动监听。

**Pointer Event（指针事件）**是浏览器描述鼠标、触摸笔等指针操作的一套事件。这里用按下、移动、松开事件完成拖动。

核心数组操作摘录如下：

```ts
const next = [...list];
const [item] = next.splice(from, 1);
next.splice(to, 0, item);
return next;
```

第一行复制原列表；第二行从原位置取出一项；第三行插到目标位置；最后返回新顺序。

**面试可以这样答：**

> 栏目和联系信息共用一个排序组件。拖动时根据指针与各行中心的位置确定目标，再更新顺序数组，简历按数组重新显示。这样两处不需要重复写排序逻辑。

如果继续追问代码里的几个词：

- **稳定 ID / React key**：每项固定的身份标识。项目经历从第三位变成第一位，身份没有变，不能仅凭“第几项”判断它是谁。
- **泛型**：组件不限定列表里必须是哪一种数据，所以栏目列表和联系字段列表都能用它。
- **Ref**：保留一个能随时读取的值，修改它本身不会触发页面更新。拖动代码用它取得最新列表和回调函数。
- **旧闭包**：函数可能记住建立时的旧数据。拖动已经交换过位置，如果还按旧数组继续算，就可能算错；读取最新的 Ref 值可以避免这里使用旧列表。
- **事件清理**：停止拖动后移除移动监听，避免鼠标以后再移动仍触发这次排序处理。

目前支持的是这些列表的排序；没有实现任意位置摆放内容、跨栏目拖动条目、完整键盘拖动或拖到边缘自动滚屏。

### 4.5 “隐藏和删除有什么区别？”

隐藏邮箱，就是把 `email` 放进“暂不显示的字段列表”。生成简历时跳过它，再打开开关就能看到原邮箱。

删除则会把内容本身清掉，这是另一种操作。

**面试可以这样答：**

> 显隐只改变展示配置，不删除原内容。渲染时先按用户配置的顺序遍历，再跳过隐藏项和空字段。

隐藏也不是权限控制：原值仍可能在导出的 JSON 和数据库记录里，不能把“看不见”说成“其他人无法取得这个数据”。

### 4.6 “照片为什么能跟着 JSON 一起导出？”

**JSON**是一种用文字记录结构化数据的格式。你可以把它理解为可以导出、重新导入的简历数据文件。它保存内容和配置，不只是页面截图。

照片的处理是：用浏览器的 `FileReader` 读取本地图片，把图片内容转成 **Data URL**，再保存到简历里。Data URL 是一串包含图片类型和图片内容的文本；其中的 **Base64** 是把二进制内容表示成文字的一种编码方式，不是加密。

**面试可以这样答：**

> 我把照片内容编码成文本放进简历数据，所以导出的 JSON 可以一起带走照片，重新导入不需要再找图片文件。实现比较直接，但照片越大，JSON、本地保存和网络请求也越大。

当前没有单独的图片上传服务、图片压缩裁剪或对象存储。对象存储就是专门存放图片、文件等内容的服务；以后可以把照片放在那里，简历里只留图片地址。这是改进方向，不能说已经做了。

### 4.7 “导入文件需要处理什么？”

导入不是把任意文件直接塞进页面，而是按下面顺序处理：

1. 读取文件中的文字。
2. 用 `JSON.parse` 把 JSON 文字转换成程序里的对象。
3. 做基础结构检查，例如有没有基本信息对象。
4. 用 `normalizeResume` 整理字段类型、补充默认配置和缺失的条目标识。
5. 用整理后的数据替换当前简历。

**规范化**就是把不完全一致的数据整理成程序约定的样子。例如老文件缺少“栏目顺序”，就补上默认顺序。本项目是自己写的整理函数，没有用 Zod；基础检查也不是对所有错误输入做严格拒绝。

**TypeScript 为什么还不够？** 它主要在开发和构建时检查代码，不能保证用户上传的文件符合约定，所以文件进入程序时还要检查。这就是“运行时检查”。

一个可以讲的具体问题是空日期：用户主动把结束日期留空，旧的默认值逻辑却可能又填回示例日期。现在会区分“明确传入空字符串”和“没有提供这个字段”，保留用户主动清空的值。

导出则反过来，把当前对象转成 JSON 文本并触发文件下载。代码中的 **Blob** 是浏览器里暂时保存文件内容的对象；**对象 URL** 是指向它的临时地址，用完会释放。

### 4.8 “模板、显示布局和图标怎么处理？”

**模板：** `sample-resume.json` 是统一的示例来源。编辑器重置为示例，以及默认简历需要回退到示例时，都读取它，避免维护两份内容不一致的模板。代码里的 `?raw` 表示让 Vite 在构建时把文件作为文本读入。

更新模板不会自动覆盖已保存的云端简历或浏览器草稿；它们是用户自己的数据。

**布局：** 左右版式用 Grid，也就是按行列安排内容的布局方式；居中版式用 Flex，也就是把一组内容沿某个方向排列，并允许换行。照片、姓名职位和联系信息按所选位置排列。

**图标：** 邮箱对应信封、电话对应听筒。图标尺寸跟随联系信息字号，并保持固定比例，长文字换行时让图标对齐第一行。

若被问到对齐细节：文字行高为 `1.35em`，图标高为 `1.05em`，上面补 `(1.35 - 1.05) / 2 = 0.15em` 的间距。`em` 是相对于当前字号的单位，所以字号调大时，图标和这段间距也一起变化。

### 4.9 “公开分享页怎么工作？”

**路由**可以理解为“某个地址对应哪个页面”。`/editor` 是编辑页，`/r/:slug` 是分享页。`slug` 就是链接里用来识别某份简历的那一段，例如 `shqingda`。

别人打开链接后，前端根据这个标识请求简历数据，再交给同一个简历组件显示。这里是浏览器取得数据后生成界面，不是后端直接生成整张简历 HTML。

默认简历读取失败时有示例或本地数据回退；其他不存在的分享标识会显示未找到。没有使用 WebSocket 这样的持续消息连接做多人同步，所以“公开分享”不能说成“实时协作”。

## 五、第二条经历怎么讲：为什么分页难，PDF 怎么导出

### 5.1 先准备一段能直接说的回答

> 简历和普通页面的区别是，它最后要落在固定大小的 A4 纸上。同样一段经历，字号或宽度变了，换行数量就变了，不能按固定条数分页。我先让浏览器把内容排出来，再读取每个内容块的实际高度，按顺序判断当前页能不能放下。栏目标题会和第一条内容一起判断，避免标题留在上一页，正文跑到下一页。

### 5.2 “测量实际高度”到底在测什么？

**DOM**是浏览器里代表网页内容的元素结构，例如一段文字、一个标题、一张图片。它不是另一份数据库。

浏览器把文字排好后，这些元素就有实际宽高。代码通过 `offsetHeight` 读取元素高度，通过 `getComputedStyle` 读取浏览器最终采用的样式，并把相关上下间距计入。

**内容块**是程序用来分页的一段整体内容，例如一个栏目标题或一条工作经历。这里把元素整理成“标识、高度、是不是标题”三项信息，再交给分页函数计算。

纸张宽度按 A4 的 210mm 设置，高度按 297mm 计算，扣掉上下留白才是能放正文的空间。预览为了适应屏幕可以缩小显示，但计算使用纸张本身的布局尺寸。

**为什么不数文字？** 同样五十个字，大字号可能占三行，小字号只占两行；再加上照片、列表和间距，只数文字不能可靠地知道高度。

### 5.3 “标题和第一条内容绑定”用一个数字例子讲清楚

假设一页能放 100 个高度单位，目前已经放了 80。接下来“工作经验”标题占 12，第一条工作经历占 30。

- 只看标题：`80 + 12 = 92`，似乎还能放下。
- 再看正文：放不下，只好去下一页，标题就被留在页尾。
- 把标题和第一条一起看：`80 + 12 + 30 = 122`，超过 100，于是在标题前换页。

核心逻辑可以简化成：

```ts
// 简化示意：标题要连同下一块一起判断。
const needed = isHeading ? headingHeight + firstEntryHeight : entryHeight;
if (usedHeight > 0 && usedHeight + needed > pageHeight) {
  startNextPage();
}
```

第一行算这次至少需要多少空间；第二行判断当前页已经有内容、并且放不下；第三行决定从下一页开始。示意中的变量和函数用于解释，不是原文件的完整代码。

**面试可以这样答：**

> 我没有让整个栏目必须在一页里，而是提前看标题后面的第一条内容。如果两者一起放不下，就在标题前换页。这样可以减少页尾只剩一个标题的情况。

### 5.4 “你用了什么分页算法？”

按当前顺序逐块处理：能放下就放当前页，放不下就换页。这类做法叫**贪心策略**，这里指每一步根据当前页剩余空间作决定，不尝试把整份简历重新排列来填满页面。

分页计算本身遍历一遍内容块。若有 `n` 个块，主要判断次数随 `n` 增长，这叫 **O(n) 时间复杂度**。它说的是这段计算，不包括浏览器测量布局或反复尝试间距的成本。

**为什么把测量和计算分开？** 浏览器测量要依赖真实页面；分页判断只需要高度数字。把后者独立成函数，就可以直接用数字测试“标题会不会被单独留下”，不用每个测试都打开网页。

这种只根据输入算出结果、不修改外部页面的函数，叫**纯函数**。

### 5.5 “预览里怎么显示换页？打印时呢？”

预览中，在需要换页的位置插入一块空白，把后面的内容推到下一页的位置。这块空白叫**分页垫片**，只用于显示，不会写进用户的简历数据。

重新测量前会先移除旧垫片，避免把之前的空白又算一次，越算越长。

打印时不再保留垫片高度，而是把它变成“这里换页”的 CSS 指令。另有两条规则：尽量不要紧接标题换页，尽量不要从一条经历中间拆页。CSS 就是控制网页样式和布局的规则。

**面试可以这样答：**

> 计算部分负责决定换页位置，预览通过空白占位表现分页，打印则把这些位置转为打印分页规则。两边沿用同一套分页判断。

### 5.6 “怎么处理末页太空、内容变化和字体加载？”

末页使用不足约 88% 时，代码会在原间距到 1.22 倍间距之间尝试调整，前提是不增加页数，让版面适当舒展。当前不是不断缩小文字来强行塞进一页。

这里用**二分尝试**：每次取候选范围的中间值，能接受就向更大间距试，不能接受就向更小间距试，代码最多尝试 9 次。面试先说明目的，不需要先背倍率和次数。

内容、版式或纸张宽度变化后会重新计算。`ResizeObserver` 是浏览器提供的尺寸变化通知工具；`document.fonts.ready` 表示页面字体加载流程完成，之后会再算一次，减少替换字体导致的误差。

**还没完全解决的情况：** 特别长的一条经历可能自己就超过一页；目前没有把它内部每条描述继续细分。照片异步加载、字体和打印设置也可能影响结果，不能保证所有内容在所有浏览器中都完全一致。

### 5.7 “为什么分成两种 PDF？”

| | A4 打印 / 另存为 PDF | 长图 PDF |
| --- | --- | --- |
| 怎么做 | 把文字和布局交给浏览器打印 | 先把简历转成图片，再放进 PDF |
| 纸张 | 标准 A4，可以多页 | 一张随内容变长的页面 |
| 文字能否复制 | 通常可以，因为仍保留文字内容 | 当前没有独立文字层，文字是图片的一部分 |
| 主要目的 | 打印和投递 | 连续浏览、展示整体排版 |

**面试可以这样答：**

> 两种需求不一样。投递用的 A4，我让浏览器直接打印文字内容，通常能保留可选择、可复制的文本；长图分享更关注连续展示，所以先生成整张图片，再放进 PDF。它们共用简历内容，但输出方式不同。

### 5.8 “A4 导出具体怎么做？”

流程是：等待字体和图片 → 创建一个看不见的小页面 → 复制简历和样式进去 → 去掉预览缩放、阴影和编辑控件 → 设置 A4 和分页规则 → 调用浏览器打印。

这个小页面是 **iframe**，可以理解为当前页面里另放的一个独立网页。这里用它隔离打印内容，防止把编辑器侧栏也打印进去。

**克隆 DOM**就是复制当前的简历元素结构；它不等于截图，所以文字仍然是文字。调用 `print()` 后会打开浏览器打印对话框，由用户选择另存为 PDF。

这不是后端生成文件，也不是保证所有招聘系统都能识别。若提到 **ATS**，它指招聘中的候选人管理系统；“PDF 有文字”不能直接推出“所有 ATS 都能正确解析”。

### 5.9 “长图导出具体怎么做？”

`modern-screenshot` 把简历页面转成 PNG 图片，`jsPDF` 再把这张图片放进 PDF 并下载。

截图前会复制简历、移到屏幕外、去掉预览缩放，并等待图片和字体。当前使用 2 倍比例生成图片，目的是增加像素数量，让放大查看时更清晰一些，代价是占用更多内存和文件空间。

PDF 宽度为 210mm，高度按图片的高宽比计算。所以它可以是一张长页面，而不是把整份简历压缩到一张 A4 上。

**要说准确：** 界面虽然叫“长图”，当前下载的文件仍然是 PDF，内部放的是图片。图片很长时，也会遇到内存和输出尺寸限制。

## 六、第三条经历怎么讲：保存、接口和冲突

### 6.1 先准备一段能直接说的回答

> 保存分为本地和云端。本地用浏览器存储保留草稿，刷新后可以恢复；云端通过接口保存到 D1，方便分享和再次读取。我没有每输入一个字就立即保存，而是等用户短暂停顿后再执行。保存到云端时会带上之前读取的版本时间，如果服务器发现版本已经变了，就返回冲突。此时前端保留当前内容并暂停自动云端保存，由用户决定是否覆盖。

### 6.2 “本地保存和云端保存有什么区别？”

**localStorage** 是浏览器给网站提供的一块本地存储，能保存文字数据。当前简历转成 JSON 后存进去，刷新页面再读出来。这叫**持久化**，意思是把内存中暂时的数据保存到能留住它的位置。

本地草稿属于当前浏览器和站点，换设备不会自动带过去；清理站点数据也可能把它清掉。

云端数据保存在 D1，通过接口读取。项目需要两者，是因为本地可以保留编辑草稿，云端可以供分享页读取。

初始化时，会检查数据库是否可用并读取云端；如果已经有本地草稿，会优先保留本地内容；没有本地草稿才使用取得的云端内容。代码里的 `hydrated` 在这里表示这次初始化流程已经完成，不是说用了服务端渲染。

这里没有实现网页离线缓存和完整的失败重试队列，所以不要把“有本地草稿”说成“整个网站在断网时都能正常打开”。

### 6.3 “为什么不每输入一个字就保存？防抖是什么？”

例如你连续输入“高级软件工程师”，没必要每输入一个字都写一次本地存储、再发一次请求。

**防抖**就是：有新变化就取消上一次等待，从这次变化开始重新计时；等一小会儿没有新变化，再执行操作。

本地保存当前约等待 350 毫秒，云端自动保存约等待 1600 毫秒。云端请求比本地写入成本更高，所以等待更长一些。

本地保存的源码摘录：

```tsx
useEffect(() => {
  if (!hydrated) return;
  const timer = window.setTimeout(() => saveLocalResume(resume), 350);
  return () => window.clearTimeout(timer);
}, [resume, hydrated]);
```

逐句理解：初始化没完成先不保存；完成后安排 350 毫秒后的保存；期间数据又变了就取消旧定时器、重新安排。`useEffect` 是 React 用来在状态变化后安排保存等操作的函数，最后一行说明它关注哪些值的变化。

**面试可以这样答：**

> 我用防抖减少连续输入时的重复保存。本地保存等短一点，云端等长一点。这样预览依然立即更新，保存操作可以稍后集中执行。

**当前实现的一个不足：** 云端保存成功会更新时间戳，进而改变保存函数；自动保存又关注这个函数，所以即使没有继续编辑，也可能再安排一次请求。因此只能说“采用防抖调度”，不能说“已经保证一次修改只保存一次”。改进可以增加“数据是否真的变了”的判断，并整理自动保存的触发条件。

### 6.4 “API、HTTP、GET、PUT 是什么？”

**API** 在这里就是浏览器和后端约定好的请求入口。浏览器按照约定的地址和数据格式提出要求，后端返回处理结果。

**HTTP** 是浏览器和服务端交换请求、响应所使用的协议。请求不仅有地址，还有方法、附加说明和可选的数据内容。

| 本项目的请求 | 作用 |
| --- | --- |
| `GET /api/health` | 检查服务和数据库是否可用。 |
| `GET /api/resumes` | 读取简历标识、分享标识和更新时间列表。 |
| `GET /api/resumes/:idOrSlug` | 读取指定简历；冒号部分代表实际标识。 |
| `PUT /api/resumes/:idOrSlug` | 提交一份简历，创建或更新记录。 |

`GET` 表示读取，`PUT` 在这里用于保存整份数据。**请求体**是这次提交的主要内容，比如简历 JSON；**请求头**是附加说明，比如内容格式和版本条件。

**状态码**是处理结果的数字标记，例如 404 表示没找到，409 在本项目中表示保存冲突，503 表示服务暂时不可用。

### 6.5 “数据库怎么设计？为什么整份存 JSON？”

目前主要是一张 `resumes` 表，每份简历对应一条记录：

| 字段 | 保存什么 |
| --- | --- |
| `id` | 内部识别这一条记录的标识。 |
| `slug` | 公开链接里的标识，不能重复。 |
| `data` | 整份简历转换后的 JSON 文本。 |
| `updated_at` | 上次更新时间，也作为保存时比较的版本。 |

`id` 的**主键**约束表示它用来唯一识别记录；`slug` 的**唯一约束**表示数据库不允许两条记录使用同一个分享标识。

**面试可以这样答：**

> 当前主要是整份读取、整份编辑、整份保存，没有按技能或公司做复杂统计的需求，所以把简历主体保存成 JSON。这样增加栏目或显示配置比较方便。代价是以后如果要跨很多份简历搜索、统计具体字段，就需要重新考虑数据结构和查询方式。

**序列化**就是用 `JSON.stringify` 把对象转成可保存的文本；读取后的 `JSON.parse` 则把文本还原成对象。`normalizeResume` 再把字段整理成程序需要的格式。

后端保存前会检查版本，通过后才执行更新。默认简历还没有记录时可以用模板初始化。代码也提供建表 SQL；**SQL** 是表达数据库查询、建表和修改操作的语言，**迁移文件**则记录需要执行的数据库结构变更。

### 6.6 “什么叫版本冲突？先别讲 If-Match”

先用两个页面解释：

1. 页面 A 和页面 B 都打开同一份简历，取得版本 1。
2. A 修改手机号并保存，云端成为版本 2。
3. B 还拿着版本 1 的内容，修改邮箱后提交整份简历。
4. 如果直接保存 B 的旧数据，A 刚改的手机号可能被覆盖回去。

因此 B 保存时会一起说明：“我是从版本 1 开始改的。”服务端发现当前已是版本 2，就先拒绝这次过期保存。

**面试可以这样答：**

> 这个检查是为了识别基于旧数据的覆盖。保存时不仅发简历，还带上自己之前读到的版本，服务器和当前版本比较，不一致就提示冲突。

### 6.7 “If-Match 是什么？你具体怎么用？”

`If-Match` 是一个 HTTP 请求头名称，表达的条件可以理解为：“只有版本对得上，才执行这次修改。”

本项目用上次更新时间当版本值，保存时把它放到请求头 `If-Match` 和请求体字段 `baseUpdatedAt` 中。服务端优先取请求体中的字符串，没有时再读请求头，然后和数据库里的更新时间比较。

**时间戳**就是表示某个时间点的值。前面的“版本 1、版本 2”只是方便理解，实际代码保存的是更新时间文本。

检测不一致就返回 409 和当前云端信息。前端把返回结果分成“成功、冲突、错误”，分别处理。

如果面试官追问标准协议：

> 这里借用了 If-Match 表达版本条件，但实现是项目自己的时间戳比较，冲突按接口约定返回 409，没有实现完整的 ETag 条件请求。

**ETag** 可以理解为服务端给某份资源某个版本的标记。知道它和版本有关即可，不要把本项目说成已经完整实现这套标准机制。

### 6.8 “冲突后，为什么本地内容没有丢？”

因为收到冲突时，代码没有用云端响应替换当前编辑内容，而是做三件事：标记冲突、显示提示、暂停自动云端保存。

本地草稿保存仍然可以继续，所以正在编辑的内容会保留在当前页面，并继续安排写入浏览器存储。

菜单里提供“覆盖保存到云端”。用户选择后，本次保存不带旧版本条件，以本地稿覆盖云端；成功后更新版本并解除冲突状态。

**面试可以这样答：**

> 我优先保住用户当前正在写的内容。发现冲突后先停下自动云端保存，不自动替换表单，再让用户决定是否覆盖。当前没有把双方修改自动合并。

**自动合并**指识别“A 改了手机号，B 改了邮箱”，最后把两边修改都保留下来。本项目没有做字段级比较、版本历史和合并界面。

### 6.9 “这样就完全解决并发保存了吗？”

**并发**指多个请求在时间上重叠进行。当前版本检查能发现部分过期保存，但还不能保证所有并发情况安全。

原因是后端目前分两步做：“先查版本，再更新”。两个请求可能同时查到相同版本，都判断通过，然后先后写入，后写的仍然可能覆盖前一个。

**原子操作**指“条件检查和修改作为不可被其他操作插进来的一步完成”。后续可以让数据库只更新指定旧版本的记录，例如：

```sql
-- 改进方案，当前代码还没有采用。
UPDATE resumes
SET data = ?, updated_at = ?
WHERE id = ? AND updated_at = ?;
```

问号是待填入的参数。最后的条件表示：不仅要找到这份简历，它的更新时间也必须仍然等于我读到的值。之后检查到底更新了几条记录；如果没有更新到，就按版本不匹配处理。

另外两个边界也要知道：不传版本或主动覆盖时，当前接口允许跳过比较；本地草稿没有连同它原先对应的云端版本一起保存，重新打开页面时也不能据此判断本地已经与云端合并。

**面试可以这样答：**

> 现在做的是过期版本检测和本地内容保护。要进一步保证并发写入，需要把版本条件放进数据库更新语句，并把本地草稿对应的基础版本一起保存。

### 6.10 “写入权限怎么做的？”

当前没有完整的账号登录和简历所有者权限控制。公开页只提供阅读界面，并不意味着后端保存接口已经受到保护。

**身份认证**是确认“你是谁”，**授权**是确认“你能不能修改这份简历”。如果把它扩展成面向多个用户的正式服务，需要补上这两部分。

如果被问到就如实说明，不要把前一个公司项目里的 SSO 登录说成本项目的能力。SSO 是单点登录，即一套登录身份用于多个系统；本项目没有做。

## 七、“怎么部署？怎么验证？”

### 7.1 部署怎么讲

> 我用 Vite 构建前端和 Worker，再通过 Wrangler 发布到 Cloudflare。前端构建文件作为静态资源提供，`/api/*` 请求由 Worker 上的 Hono 处理，Worker 通过绑定访问 D1。

**静态资源**就是构建出来的 HTML、JavaScript、CSS 等文件。**构建**是把开发时的代码处理成浏览器和运行平台能使用的发布产物。

**数据库绑定**是配置好“这个 Worker 使用哪一个 D1 数据库”，代码中通过 `DB` 这个名字访问它。

**SPA** 是单页应用：不同地址主要由浏览器中的前端路由决定显示内容。这里配置地址回退到前端入口，保证直接打开分享页地址时也能进入应用，再由页面请求简历数据。

实际发布命令是 `pnpm run deploy`。更新网站或示例模板，不会主动覆盖 D1 里已有的简历记录。

### 7.2 测试怎么讲

> 我把能独立计算的逻辑拆出来测试，比如标题和首条内容放不下时是否一起换页、空日期是否被错误补回、旧版本保存是否返回冲突。接口和保存流程也有测试。字号、图标对齐、实际分页和打印效果还需要在浏览器里检查。

**单元测试**是给一小段逻辑输入，检查输出是否符合预期。**Mock** 是测试中的替代对象，例如用一个可控制的假接口返回冲突，从而检查前端是否保留本地内容。

仓库使用 Vitest 执行测试。测试重点包括数据整理、本地存储、API 客户端、保存流程、分页计算和版本比较。现有导出测试覆盖范围较小，不能据此说所有 PDF 场景都测过。

`pnpm check` 会运行类型检查、测试和构建。面试时以实际执行结果为准，不把旧的测试次数当成永远不变的指标。

## 八、面试常见追问：先练这些短回答

### “你觉得这个项目最有技术含量的地方是什么？”

> 我会重点讲分页和保存。分页要根据真实排版结果判断，不能只按文字数量；保存要区分当前编辑内容、本地草稿和云端版本，尤其是冲突时不能直接把用户正在写的内容替换掉。

### “能不能讲一个具体遇到的问题？”

> 一个具体问题是标题和正文被分到两页。只看标题高度时，它在上一页还放得下，但后面第一条经历放不下。我改成把标题和紧接的一条内容一起判断，放不下就从标题前换页。

如果被问“怎么验证”，接着说：用高度数字构造“标题单独能放下、加上正文放不下”的测试，再看真实简历的浏览器分页效果。

另一个可讲的问题是“用户清空结束日期，旧示例日期又被填回”。关键是区分空字符串和缺失字段，而不是把所有空值都当成需要补默认值。

### “为什么不用一个 PDF 库全做完？”

> PDF 是文件格式，不代表里面一定是可复制的文字。把截图放进 PDF 很直接，但文字变成图片；A4 投递希望保留文本，所以用了浏览器打印。两条路径是按输出需求分的。

### “为什么不拆很多张数据库表？”

> 当前操作单位是一整份简历，先整份保存比较符合需求。如果以后要跨用户按技能、公司做搜索统计，再考虑把需要查询的字段拆出来。

### “网络不好会怎样？”

> 当前页面里的编辑和预览不依赖每次请求成功，本地也会保存草稿。云端没保存成功时，分享页不会因此自动得到最新内容。项目还没有完整的离线打开和可靠重试队列。

### “以后优先改什么？”

> 如果要给更多用户使用，我会先补登录和写入权限，然后把版本检查改为数据库条件更新。前端会处理无修改仍可能重复自动保存的问题，再完善长内容分页、图片存储和冲突处理界面。

### “项目上线后效果怎么样？有多少用户？”

已经可以说“部署上线、能完成编辑、分享和导出”。用户量、节省时间、性能提升比例等，只有你有真实记录时才说；当前代码和部署结果不能证明这些数字。

## 九、面试前怎么练，不用死背全文

第一遍只看第二节，把项目介绍说顺。第二遍分别用一分钟讲清楚“修改手机号后发生什么”“一页放不下时怎么办”“两个页面先后保存会怎样”。第三遍再补技术名词和代码细节。

检查自己能不能不用术语回答下面六个问题：

1. 这个工具是给谁用的，能完成什么？
2. React、Hono、Drizzle、D1 分别负责哪一步？
3. 为什么预览可以马上变，云端保存却可以晚一点？
4. 为什么标题要和第一条内容一起判断？
5. 为什么同样叫 PDF，有的能复制文字，有的不能？
6. 为什么保存时要带旧版本，发现冲突后保留了什么？

回答时先说具体操作，再说实现。比如先说“停下来 350 毫秒再保存”，再补充“这是防抖”；先说“服务器发现你基于旧数据修改”，再补充“这是版本冲突”。这样你自己和面试官都更容易跟上。
